## 2. 项目的模块边界

| 模块 | 实际责任 | 对本次修改的约束 |
| --- | --- | --- |
| `backend/apps/gateway` | 唯一组合根，依次组装 Host、Store、Provider、Core、Admin、API 和 Worker | 不在这里增加统计业务 |
| `gateway-protocol` / `gateway-api` | 共享协议事实；HTTP、SSE、WS 与身份/响应边界 | 不直接读插件 SQLite，不解析统计业务 |
| `gateway-core` | 请求快照、账号授权范围、准入、attempt、重试与交付屏障、计量 | 保持会话、工具副作用、已交付输出及重放规则 |
| `providers/openai` / `providers/xai` | 各自凭据、选号、目录、额度、上游传输与协议差异 | 网关池真实访问计时属于 OpenAI 传输桥，不能放进通用 Core |
| `gateway-admin` | 账号/分组/Key/设置/备份/用量等用例与端口 | 继续拥有通用管理规则，不建立第二套账号目录 |
| `gateway-store` | PostgreSQL、Redis、对象存储适配器 | 不把插件观测塞进公共账号行解析或费用账本 |
| `gateway-host` | 配置、日志、HTTP 排空、Worker 监督、更新和外部服务适配 | 统计不能延长流式关闭或改变进程恢复规则 |
| `frontend` | 登录、路由、布局、主题、基础组件、插件管理和页面生命周期 | 使用现有主壳，不新建 Vue 应用、导航或登录态 |
| `plugins/<id>/ui` | 各功能的页面、表单、组合式函数、领域展示 | 网关池页面和新图表继续放在自身插件目录 |
| `packages/plugin-sdk` | 命名能力桥、操作映射、宿主授权、可见性与轮询 | 新统计必须经能力桥，并声明平台兼容要求 |
| `packages/ui-kit` | 跨页面领域组件和格式化工具 | 复用现有工具，不为单个统计页面新增通用框架 |
| `services/plugin_host` | 版本控制面、任务、Worker 生命周期适配、网关池持久化 | 负责统计事实保存和管理查询，是平台代码，UI 包不能替换它 |
| `services/updater` | 包校验、不可变版本、租约、恢复、原生 Worker 与 A/B 发布 | UI 热更新、控制面更新、Rust 发布是三个边界 |
| `services/egress` | VLESS/Hysteria2 经 sing-box 提供本机 CONNECT 出口 | 与上游 unified 网关池是不同概念，不纳入本次统计 |

通用管理写入沿 API → Admin → Store 执行，在事务内更新事实、审计和必要的 revision，提交后发布运行快照。推理请求冻结快照，Provider 返回冷流，Core 控制发送与下游提交；输出交付后不能为统计或轮转任意重试。

主业务数据在 PostgreSQL，准入/租约/亲和等协调状态在 Redis；网关池现有的组合、票、租约、冷却和观测另由控制面的私有 SQLite 管理。三者不能因都有“账号”和“时长”而合并所有权。

## 3. 插件管理如何影响这次开发

当前网关池清单为 `protocol: 2`、`sdk: 1`、`runtime: vue-component`、`hostApi: 1`，页面是 `/extensions/gateway-pool`。

加载链路：

```text
PluginManager 安装已校验归档
  → StaticPluginStore 保存按 SHA256 标识的内容版本，切换 current
  → 主壳目录和 PluginRoute 选择页面
  → componentResources 校验组件工厂、共享依赖和 hostApi
  → SDK 按页面所属插件/内容版本调用命名能力
  → Python 校验启用状态、能力及实际登录角色
  → 网关池本地持久化，或转发 Rust 管理 API
```

- Vue、Router、Pinia、登录/主题状态和基础 UI 组件由主壳共享。`build-plugin.mjs` 构建的是组件工厂，不是完整网站。
- 页面和后台任务绑定具体内容版本。安装新包不会销毁当前编辑页；重新打开页面使用新版本，旧页面由租约继续保留。
- 当前版、上一版及仍有租约的版本分别保留。回退切换包版本，不回退业务历史数据。
- 代码预载不查询业务，页面首次进入才加载数据，切页保留状态；不可见时暂停业务轮询。
- 主壳共享组件接口无变化时，不需要为新增网关池图表重编主壳。新增控制面能力需先升级平台，不能只上传 UI 包。

参考源码：`frontend/src/plugins/PluginManager.vue`、`pageResources.ts`、`componentResources.ts`、`componentRuntime.ts`，以及 `services/plugin_host/server.py`、`services/updater/static_plugins.py`。

## 4. 网关池现有业务链路

```text
账号资格/分组/权限检查
  → 查询候选目录，plan / claim 获取准备租约
  → 取池 Cookie → bootstrap 取 S0 → 携票 replay 判定
  → 21 发布 ready 窗口，旧窗口退役
  → reserve 业务租约，其他模型按需拿自己的票
  → sent 复核发送许可 → 实际发起业务 → 响应头判定
  → 正常 SSE 继续交付，结束/取消时 finish 归还租约
  → 退役组合排空 → cooling → 到期后再次找票
```

已核实的关键事实：

1. 当前控制面以所有已纳入池的账号为范围共享一个服务窗口；`claim` 和 `probeResult` 会检查/退役其他账号的组合，没有按每个账号建立独立并行池。因此“每个账号的轮次”是统计维度，不能改变现有全局窗口调度。
2. 组合用 `accountId × gateway` 标识，每次准备另有 `generation`。票按模型存储、窗口共用，换代后票作废；一个业务租约可能先拿票，再发送真实业务。
3. `sent` 是发送前的许可与保守接触标记，调用成功不证明上游已收到业务。新计时需在 Rust 的发送执行、收头、流结束处记录事实，不能把控制面收到 RPC 的时间当作精确网络事件。
4. 窗口计时从首次上游发送标记开始，包括 bootstrap；默认 180 秒只是开始准备备用票的阈值，窗口用满后当前窗口继续服务，直到遇到 29、失败、Cookie 将到期、一轮结束或账号退出调度（0.5.0）。备用票转正的窗口从它的第一次业务访问开始计时，备用期间不计入。
5. 退役后不再接新业务，但已有请求继续。冷却从最后一次真实访问结束后开始；失联租约当前采用保守超时点恢复冷却，不能把该点冒充真实完成时刻。
6. 静置从起始档（默认 2h）开始，复测仍 29 时按加性（默认，每次加步长，默认 1h）或乘性（翻倍）升档，上限默认 24h；检测失败固定静置 5 分钟，不升档。同一组合连续两次在同一档恢复，下次起始档降一档（0.5.0）。
7. 池目录/Cookie 获取失败而没有访问上游时，不重置真实静置。短暂重试等待不能展示为一次新的上游冷却。
8. 21/29 是响应头实验分类；bootstrap 和其他模型拿票不按返回 state 判断 29。21 也不等于客户端最终流成功。
9. 组合冷却与账号额度重置、Redis 限流/容量冻结是不同状态，冷却恢复记录只记录网关池组合的静置/复测。
10. 当前页面读取最多最近 200 条观测/切换；这些样本不能计算完整总计。`businessResult.durationMs` 到响应头为止，`previousWindowSeconds` 可能跨入等待或静置，均不能直接作为本次目标指标。

## 5. 用户已确认的需求与本方案的补充定义

已确认：

- 全账号、全网关轮转明细，可筛选
- 每个账号的网关使用汇总改为图表，同时能查看每批轮转记录
- 账号汇总中的冷却规律图表与网关卡片按需查看的最近记录
- 放入网关池现有 tab，将“切换记录”换掉
- 同账号同网关的业务间隔不足 2 小时且没有用尽/切换/退役，归同一小汇总；闲置达到 2 小时结束
- 大汇总以单个账号走完一轮网关为单位

用户以“开始修改”授权按本方案实施；界面视觉效果待本地预览确认。

### 三个层级分别保存

| 层级 | 含义 | 编号依据 |
| --- | --- | --- |
| 使用小汇总 | 同账号同网关的一段连续业务使用 | 独立 segment ID，不直接等同于 generation |
| 轮转记录 | 一次候选准备及其窗口生命周期；失败准备也留记录 | generation；展开查看关联的小汇总 |
| 账号批次 | 一个账号的一轮候选遍历，包含多次轮转记录 | 持久 batch ID + 账号内递增编号 |

一般一条轮转记录对应一个使用小汇总；未用就失败的准备没有业务段。若同一运行代次闲置满 2 小时后再次接到业务，必须产生新的小汇总，不能仅给旧行增加 idle 标签。这样既保留完整轮转时间线，也不会把同一个窗口复制计时。

### 小汇总规则

- 首次业务发送执行开始建立业务段，探测/拿票单独记账
- 有业务在途时不算闲置；闲置起点是最后一个业务请求结束
- 空闲间隔 `< 7200s` 继续同段，`>= 7200s` 结束旧段
- 空闲段业务终点是末次业务结束，另记满两小时的结算边界，不把两小时补进业务用时
- 用尽、切换、退役立即关闭该段的新请求归属，尾部在途仍归原段，排空后补齐终态
- 连续模式的后台探测不能替业务段续命；两小时只是统计分段，不主动退役窗口或调整冷却
- 关闭浏览器不影响分段。由控制面维护边界，空闲边界可在下一次事件/查询时按已存时间确定性补结算，写入前重新核对在途事实，不依赖前端定时器
- 没有实际观测到账号停用/额度用尽时不猜测原因；不得为了补一个结束标签修改账号调度策略

### 批次规则：按冻结候选集合累计完成度

1. 账号第一条准备记录建立批次，保存当时有效目录与限定规则得到的候选集合快照
2. 候选只有在实际探测得出结果，或成功窗口退役并排空后才记为本批已处理；分别标记已服务、29、检测失败，失败不冒充已服务
3. 仅在冷却、排队、目录暂时缺失时仍是未遍历；已完成候选再次被调度仍归当前未完成批次，不能一重复就开下一批
4. 快照中全部候选处理完成、该批所有访问排空后，批次完成；之后该账号下一次准备开启新批
5. 自然目录新增不扩张当前批，下一批再纳入；暂时消失保留待处理标记。明确配置变更/停用使范围失效时结为中断，不能显示“完整走完”
6. 两小时闲置或暂时换到另一个账号，结束相应使用段，但不自动宣告该账号整轮完成
7. 批次号不随时间筛选、分页或重启重新编号。全账号视图同时显示账号和批次，避免不同账号的“第 3 批”混淆

现有调度优先 Cookie 余量和最久未访问，不保证轮询覆盖所有候选，因此一批可能长时间未完成。界面如实显示覆盖度与待处理网关；为使批次更快完成而改变调度属于额外功能。

## 6. 时间统计口径

| 指标 | 起止与累计规则 | 不包含/不能替代 |
| --- | --- | --- |
| 找票耗时 | 每个候选从开始准备到判定/失败，含取 Cookie、bootstrap、replay 和该准备内重试；汇总累计所有候选，不能只算最终成功者 | 不含开始准备前等待冷却/等待账号的时间，不等于客户端总等待 |
| 模型拿票耗时 | 已有窗口中，为其他模型单独取票的发送执行至收头/失败 | 不混入初始找票或真实业务 |
| 窗口时长 | 验证成功的代次，从窗口计时起点（备用票转正的窗口取第一次业务访问，其余取首次上游访问）起，计到最后一次确认可用的时刻：最后一个判定为 21 的业务访问结束时，没有业务访问时为验证时刻；以 29 结束止于最后一次 21 的结束。进行中且窗口未超过 `windowSeconds`、有在途请求、或最近 `windowSeconds` 内有使用的窗口计到查询时刻。之后又被使用且仍为 21，从新的确认时刻继续算 | 不用配置 180 秒直接填值；失败准备无有效窗口；从未转正的备用票时长为 0，不计缺失 |
| 排空尾时长 | 退役至该代次最后一个在途访问结束 | 单列，冷却不能在排空前开始 |
| 业务使用时长 | 同一使用段内已记录业务发送执行至流结束/失败/取消的区间并集，并发不重复 | 排除找票、拿票、空闲；不是收头耗时或纯模型计算时长 |
| 请求耗时合计 | 每次业务尝试耗时逐项相加，详情辅助指标 | 并发时可能超过业务使用时长 |
| 整轮跨度 | 本批首次准备至全部完成/中断；进行中显示截至当前 | 含等待和冷却，不是前三项相加 |

共同规则：

- “使用总时长”默认指业务使用时长；窗口总时长、找票总耗时分别展示
- 一个窗口可以包含多个业务段，窗口总计按 generation 计一次；跨账号/网关合计明确为组合时长合计，不能称为整个池的运行时间
- 找票与窗口有重叠，业务通常在窗口内但可延伸到排空尾部；三者不可堆叠为总时长或做同一个饼图
- 请求数按已开始的业务尝试统计，名称用“业务请求次数”，不混入探测/拿票；内部重放可能多次，不冒充客户端独立请求数
- 历史时间点用 UTC 时间戳，页面按现有时间工具显示；单次真实耗时由 Rust 单调时钟测量，终态记录在发出 RPC 前生成，避免 RPC 排队被算进 SSE
- 统计保留发送状态、响应头分类和流终态三个独立事实；结果未知、失联回收、旧协议数据标记不完整，不补零或用租约过期时间伪造完整耗时
- 时间筛选按区间交集累计，次数按发送起点归属；跨范围记录标注“部分计入”，批次真实状态与本次查询覆盖度分开
- 提供“全部已采集”及自定义范围。明细分页，累计不截成最近 200 条或无说明地限制为 31 天；长范围聚合采用有界查询，必要时明确提示缩小范围，不返回伪完整总数

校验例：业务 A 为 10:00–10:02，B 为 10:01–10:03，则业务使用 3 分钟，请求耗时合计 4 分钟。10:03 结束后到 12:03 没有业务，旧段结算，其业务终点仍为 10:03。

## 7. 冷却恢复记录

历史按账号 × 网关 × 冷却周期保存，在账号汇总中聚合展示，并在账号与网关卡片按需查看单个网关记录，不另设冷却表。

网关标签：编号、状态配色与剩余静置时间。账号默认收起，标签区限高滚动，适配约 100 个网关。

点击网关块展开当前状态（含备用票）、当前档、起始档、静置原因、下次可复测时间，以及最近 5 个静置周期的完整历史：每一轮的静置起点、原因、档位变化、计划与实际复测时间、结果（21/29/失败及状态码与失败类别）。

- **本档实际静置**：上次真实上游访问结束 → 本次复测实际开始
- **到期后等待**：计划可复测时间 → 实际复测开始，反映懒模式无流量或调度延迟
- **恢复跨度**：本周期首次冷却起点 → 首次观测 21，包括多档等待与探测
- 到期未测显示“待复测”，不显示“已恢复”
- 21 是首次观测恢复时间，不是精确的上游恢复时刻；第一次找票成功但此前无冷却，不算恢复
- 静置中任何真实访问重新起算下一段，保存原因；仅失败于池服务而未访问上游，不生成伪静置段
- 丢失完成回报时，区分保守调度时间与未知的实际静置时间
- 读取页面不创建探测或租约，不改变持续模式和退避规则；没有实际再访问时不生成间隔或恢复结论
- 每一步静置记录原因（29、失败、轮换、备用票过期等）、所在的档、当时的起始档；复测失败另记失败类别与状态码。检测失败后的 5 分钟复测按实际间隔进入冷却汇总，不单独剔除

## 8. 页面展示

顶层标签为“账号与网关 / 轮转明细 / 轮转统计”。界面只展示窗口时长和简单冷却汇总；第 6、7 节保留底层历史合同及采集语义。

- 账号与网关：账号卡片默认收起，展开后网关标签限高滚动。选中单个网关显示当前冷却和最近一次实际再访问结果。
- 轮转明细：账号、网关/批次、窗口起止、窗口时长、状态与详情入口。支持时间、账号、网关、批次筛选与分页。详情单层展开验证时间、结束原因、检测结论及该代次检测/访问记录，保留时间、类型、模型、结果和是否返回 state；不展示其他耗时字段。失败检测显示未形成窗口，不伪造窗口时间。
- 轮转统计：网关窗口时长环图与“最近 24 小时每个账号各网关的窗口时长”（同一窗口时长口径，不受页面筛选影响），指标固定为窗口时长，不提供指标切换。批次表仅保留批次、已使用网关、窗口总时长、状态和明细入口。
- 冷却汇总：保留按实际再访问间隔分组的恢复比例柱图与判定样本数，分组为不足 2h、2–4h、4–8h、8–16h、16h 及以上，无判定样本留空。上方显示已恢复/判定次数、总体恢复比例及恢复样本间隔中位数；失败、待结果和缺失间隔在必要时提示。

窗口时长按第 6 节口径计到最后一次确认可用；仅验证成功的代次形成窗口（备用票转正后才有窗口）。轮转明细每行另有备用票拿到时间、启用时间、最后确认可用时间。筛选按交集累计，范围合计覆盖完整匹配结果，缺失窗口时间不补零。

保留底层历史合同与已采集事实兼容，不因显示简化改变选号、退避和持续模式。冷却统计按真实访问记录计算，页面查询不触发上游探测。

UI 复用现有基础组件、主题 Token、圆角、日期与时长工具。查询序号校验阻止过期结果覆盖新筛选，后台刷新不重置分页，非活动视图暂停历史轮询。

## 9. 最小实现范围与兼容方案

| 位置 | 计划修改 | 发布边界 |
| --- | --- | --- |
| `plugins/gateway-pool/ui/page/` | 页面入口、图表、明细/批次表、网关冷却汇总、类型与查询逻辑 | 网关池 UI 包 |
| `plugins/gateway-pool/plugin.json` | 新统计能力、版本、发布时间、说明 | 同一 UI 包 |
| `plugins/gateway-pool/service/src/history.rs`、`history_query.rs` | 记录事实、使用段/批次/冷却持久化、分页/汇总 | 网关池服务插件 |
| `services/plugin_host/server.py` | 把 `gateway-pool.*` 转给服务插件 | 插件控制面 |
| `packages/plugin-sdk/policies.json` / `operations.json` | 授权并登记统计能力 | 宿主平台 |
| `backend/crates/providers/openai/src/provider/plugin_routing.rs`（钩子桥） | 区分探测/拿票/业务，发送与流终态时间、结果经钩子回报 | Rust 网关 |

统计能力为 `gateway-pool.history.read`，明确声明使缺少统计支持的旧平台在安装阶段拒绝新包。原有 `gateway-pool.read` 合同保留。

持久化设计约束：

1. 在现有私有 SQLite 追加带版本的历史结构，不修改 PostgreSQL 冻结迁移，不改变费用账本
2. 保存批次快照、轮转代次、使用段、实际访问和冷却复测事实；主键关联使用 account/generation/lease/access-sequence，重复回报幂等，重试访问不挤成一条
3. 两个 A/B 网关共用控制面事实，不能只用 Rust 或 Python 单进程内存编号
4. 运行状态保持现有唯一所有权，历史模块不重新计算路由/退避；写入只追加有界事实，不在 sent/finish 中扫描整段历史
5. 历史查询使用独立只读快照、索引和服务端分页；现有 `BEGIN IMMEDIATE` 适合状态更新，不适合承载长范围报表。如需补结算，先做短事务，再离开写锁聚合
6. 采集失败可报告缺口，但不得因为新增报表写入失败回滚已成功的租约归还、把已交付请求改成失败或重新发送；原有材料/路由安全失败仍按原规则处理
7. 保留 `recordedSince`、字段协议版本和缺口原因。旧程序/旧数据只返回确实掌握的字段，不用观测样本伪造完整历史
8. 账号标识稳定，显示名来自既有目录及必要的历史展示快照；删除/归档后仍可查历史。数据中不复制 Cookie、state、Token、请求正文
9. UI 回退不删除新历史表；旧控制面/旧网关兼容追加字段，混合版本明确标记计时缺失。验证回退和再次升级不会重复计时

首次交付依赖控制面能力与 Rust 计时支持；后续只调整图表可以独立热更新插件包。这里没有扩大到全面插件化迁移。

## 11. 实施次序与成功标准

1. **先固定数据合同**：以本方案给出小段/代次/批次及时间字段，补充边界案例 → 能明确解释同一代次闲置、并发请求、旧窗口排空和不完整批次
2. **接入记录与查询**：追加 SQLite 结构，Rust 采集真实阶段，控制面只读聚合 → 重启、A/B、重复回报不重算，统计失败不影响已交付结果
3. **实现插件内界面**：用现有组件替换第三个 tab，账号汇总使用双图 → 筛选、图例钻取、批次详情、冷却详情同口径
4. **本地真实插件预览**：先恢复隔离主壳/控制面环境，安装构建出的网关池包，通过 `/extensions/gateway-pool` 查看 → 样式、能力桥、版本租约都来自实际平台；模拟数据必须显式标注
5. **预览确认后的发布**：按依赖先准备兼容控制面和计时网关，再安装新 UI；候选在独立端口验收，通过后按 A/B 交接 → 旧请求排空、可回退、数据保留。预览确认不等于 GitHub push 授权

必要验证范围：

- Python：复用现有 26 项网关池测试，新增小段 7199/7200 秒、在途跨边界、并发区间合并、候选重复/变化、批次编号稳定、冷却多档/未发送失败、重复回报、丢终态、只读查询与写入并发
- Rust：遵循 `scripts/build-local.ps1`，对 OpenAI 传输桥做检查及 mock 回归，确认拿票不计业务、收头不结束流、取消/29 重放记录准确、不碰工具副作用/已交付输出边界；不运行需真实授权的 ignored 上游实验
- 前端：单插件 `check-plugin.mjs`、相关 lint、`build-plugin.mjs`；验证混合版本、失序查询、空/缺失/跨范围数据与图表合计。共享接口没改时不扩大到逐页浏览器验收
- 包：验证缺少能力时拒绝安装、旧页面租约、重新打开生效、UI 回退保留历史；不把单插件类型检查当成后端计时验证
